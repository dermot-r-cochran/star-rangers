# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

*Fian Ilchruinne* is an Eleventy (11ty)-powered interactive science-fantasy novel site. The repo is both the publishing engine (MIT-licensed) and the story content itself (CC BY-NC-ND 4.0, with a Fan Works exception — see `CONTENT-LICENSE.md`).

**The work is titled *Fian Ilchruinne*; the Star Rangers are an organisation inside it.** Title history: retitled from *Star Rangers* to *Drithane* on 2026-08-01 (clearing Andre Norton's 1953 novel *Star Rangers* and a 1987 comic of the same name); *Fian-ilchruinne* adopted as the setting umbrella 2026-08-03; and on 2026-08-04 *Drithane* was retired as not unique enough (Google silently corrects it to *Dithane*, a fungicide), leaving Fian Ilchruinne as both umbrella and title — full path in `story-bible/the-title-and-its-risk.md`. **"Drithane" has been named into canon as a planet** (2026-08-04, same day it was freed): the Celtic Union charter world at `src/lore/planets/drithane.md`, named in-world from the same *drithle* root. In-world it now means only that planet — don't reintroduce it as a title or setting descriptor. Only front-of-house branding has ever moved: the corps keeps its name throughout the fiction, and the repo slug (`star-rangers`), the `/star-rangers/` URL prefix, the alias domains and the giscus comment repos are all deliberately unchanged. When editing, ask which sense a given "Star Rangers" carries — the work's former-title surfaces (rename) or the in-universe corps (leave alone). Content and code are deliberately separated so the engine can be forked without implying rights over the story; see `FORKING.md` and the License section of `README.md` for the exact path split.

The site is built from Markdown content with Nunjucks (`.njk`) layouts, rendered by Eleventy 3, and deployed to several independently-branded production domains (plus GitHub Pages) from one codebase — see "Multi-domain deployment" below.

## Authority and review boundary

Dermot is the author; this file's other sections grant a lot of standing permission, and this section says where that permission stops. It exists because the boundary was operating tacitly — the external half is now written down in `CONTRIBUTING.md` (no third-party PRs, forks unsupported), and this is the internal half. Work in the first tier, propose in the second, and don't do the third without being asked in the session you're in.

**Merge policy across the first two tiers** (Dermot's direction, 2026-09-04: *"auto merge PRs unless there is an open decision for me to review first"* — `story-bible/decision-making.md`). A PR merges when CI is green, whichever tier it falls in, **unless it carries a decision that is his and not yet made** — a reading not yet confirmed, a judgement call flagged for his eye, a choice among shapes put to him. Then it stops, and the PR body names the decision. This supersedes the second tier's older default below ("draft it and stop"), which dates from when every draft was a proposal; a draft is now a proposal only while something in it is open. The boundary of *what is his* is unchanged — the seven kinds in the working folder's `TODO.md` and the never-without-instruction list below — only the default for a PR with nothing open in it.

**Proceed and merge when CI is green** — open a PR as usual, merge it once checks pass, no wait required:

- Engine and tooling: `.eleventy.js`, `lib/`, `scripts/`, `.github/`, dependencies, the deploy scripts, CI.
- Documentation and templates: `README.md`, `TECHNICAL-README.md`, `FORKING.md`, this file, `sample-*.conf` / `sample-*.json`, and `CHANGELOG.md` entries recording work already done.
- Mechanical content fixes that assert nothing new: broken internal links, stale `related:` terms, an `image_alt` corrected to match what the image actually shows, typos, and terminology sweeps that apply an already-settled rename from the canonical glossary's migration map.
- Technical or restorative image work: resizing/recompressing to the conventions above, regenerating a codex title card with `scripts/make-codex-cover.ps1`.

**Draft it and say what it commits to** — open a PR, describe what it commits the story to, and (since 2026-09-04) merge when green unless something in it is open for Dermot, in which case stop and name it:

- Anything that asserts a fact about the world: new or changed `src/lore/`, `src/glossary/`, `src/codex/`, `src/timeline/` entries, and any `canon_facts`.
- Narrative prose. The 2026-07-25 standing permission covers *drafting* without being asked; it does not cover merging. Every draft is a proposal.
- New character portraits, and any new image that reads as a depiction of a character or place.
- Policy, licence and promise-making documents — `CONTRIBUTING.md`, `CONTENT-LICENSE.md`, `FORKING.md`'s terms, the About page's commitments. These bind him to other people.
- Registering or re-pointing a domain or edition in `lib/editions.js`. An edition entry is a decision about a live site, which is exactly why it moved into the repo.

**Never without an explicit instruction in the current session:**

- Rewriting published git history. Roughly 200 old commits carry real email addresses; that was reviewed and deliberately left as-is — don't re-propose a rewrite.
- Force-pushing `main`, deleting branches or tags anyone else may hold, or cutting a release tag.
- Moving a thread's `tier` gate, or an edition's `tier`, in a way that changes who sees the church-space thread. A tier is a decision about who a readership is, not a config tweak.
- Taking published content off a production domain, or changing a live domain's identity.

Two things that make the line land where it does:

- **The gates prove structure, not judgement.** `validate-content.js`, the Eleventy dry run, `check-internal-links.js` and `check-related-terms.js` can show that a page is well-formed, uniquely identified and fully resolved. Nothing in the toolchain can show that a sentence is *true in this world*, in the house voice, or safe to be bound by later. So mechanical correctness is delegable and assertions about the world are not — that is the whole rule, and the tiers above are just its consequences.
- **Merging is publication-adjacent.** Production clones deploy from this branch, so a merge is the last reviewable moment before content reaches live domains — one reason the second tier stops at the PR rather than at the commit.

And in every tier: **say what you did.** A session that drafts narrative, changes canon, or touches a live domain's configuration reports it plainly, so nothing lands by default because nobody noticed it.

### Authoring checkers and local tools

These live in `scripts/` and exist so recurring authoring chores don't get re-invented each session. Since 2026-08-24 the first two are **part of `npm test`** and the third is **a CI gate** (run after `generate-themes` in the same job, which is what makes it correct — see below); `list-canon-facts.js`, the `.ps1` tools and the image-pipeline `.js` tools below remain local-only:

```bash
node scripts/check-internal-links.js    # verify every internal /star-rangers/ link in src/ AND lib/ resolves (in npm test since 2026-08-24)
node scripts/check-related-terms.js     # verify every front-matter `related:` term matches a real page title (in npm test since 2026-08-24)
node scripts/check-contrast.js          # check every palette in src/css/ against WCAG 2.2 AA (4.5:1) on the pairs main.css actually composes; run after editing a palette AND `npm run generate-themes`, since it reads the generated files (CI runs exactly that sequence, plus a git-diff drift check that a theme-*.css wasn't hand-edited)
node scripts/list-canon-facts.js        # aggregate every chapter's canon_facts in story order; optional term filter (e.g. `-- rescue`) for the spoiler test — informational, never a gate
```
```powershell
.\scripts\import-image.ps1 -In "$env:USERPROFILE\Downloads\x.png" -Out src\images\characters\y.jpg -MaxEdge 1200
.\scripts\make-codex-cover.ps1 -TitleLines "TITLE","LINE TWO" -Category "SURVEY RECORDS" -Subtitle "..." -Institution "..." -Author "..." -Stamp "OFFICIAL" -Motif rules -Out src\images\codex\z.jpg
.\scripts\make-lore-cards.ps1 -List          # batch driver over make-codex-cover.ps1; -List to preview, -Force to overwrite
.\scripts\make-emblem-card.ps1 -List         # 1600×900 landscape emblem cards for identity-bearing lore entries; -List prints the device vocabulary
.\scripts\make-placeholder-card.ps1          # PORTRAIT/ILLUSTRATION PENDING cards, stamped so the image queue counts them as unfinished
.\scripts\image-file.ps1                     # files a generated/downloaded image into the right src/images/ subdir at the right size and stages it on a branch
```
```bash
node scripts/image-prompts.js           # work through the prompts already written in story-bible/images.md — clipboard one at a time, or generate via Gemini (untracked gemini.local.json; sample in scripts/)
node scripts/build-photo-catalogue.js   # rebuild story-bible/own-photography.json from the sibling dermot-cochran-photography checkout, so the pipeline offers Dermot's own photos before generating
node scripts/mark-placeholder.js        # stamp a JPEG's COM segment as PLACEHOLDER so the image queue stops counting it as finished work
```

The six `.ps1` tools are Windows-only (System.Drawing/GDI+), matching the author's environment; all the `.js` tools run anywhere. The three image-pipeline `.js` tools and the three newer `.ps1` tools arrived together on 2026-08-21, each header marked LOCAL AUTHORING TOOL — none is part of the build, `npm test`, or CI. `make-lore-cards.ps1` carries its own card table inline (nine lore entries lacking an image) and skips files that already exist unless `-Force`, so a re-run can't clobber a card replaced by hand. `make-codex-cover.ps1` also takes **`-Underlay <path>`** (added 2026-08-20), which puts a photograph behind the lettering — centre-cropped to the square, scrimmed heaviest where the type sits — so it composites picture-led cards as well as designed ones. That exists because a generator cannot spell: generate the picture wordless, set the words here. Note the split of card generators: `make-codex-cover.ps1` emits a square 1600×1600 card in one fixed blue palette with no emblem — codex-style — while the landscape 1600×900 ringed-emblem lore cards, whose original recipe is unrecorded, now have their own generator in **`make-emblem-card.ps1`** (added 2026-08-21 as the landscape/emblem mode that `make-lore-cards.ps1`'s header left open). Its device vocabulary is deliberately geometric — rings, spheres, arcs, chevrons, dot fields — because GDI+ primitives can draw those exactly where an image model cannot, and its epithet/qualifier lines are **authored, not derived**: pass them in, don't invent them. (Two non-tools also live in `scripts/`: `alias-notice/`, the templated redirect page `cpanel-deploy.sh` installs on decommissioned alias domains, and `giscus-welcome-posts.md`, authored copy for the comment boards.) Each checker catches a failure mode `npm test` structurally cannot:

- `check-internal-links.js` — front-matter validation and the Eleventy dry run both pass while a cross-link points at a page that was renamed or never written. Scans **`src/` and `lib/`** (`.md`/`.njk`/`.html`/`.js`), because authored copy with links in it is not confined to `src/` — `lib/editions.js` holds the per-domain homepage taglines. Scanning by root rather than by a hand-list of exceptions is deliberate: a list of exceptions goes stale, and the next authored file outside `src/` would silently leave coverage. One consequence: an illustrative URL written in attribute form (`href="…"`) inside a code comment gets checked like a real link, so describe a fake path in prose rather than quoting it.
- `check-contrast.js` — a palette is chosen against the page background, and every colour in it then also lands on `--color-surface-2`, two steps darker, where badges and chapter labels sit. Nothing in the toolchain can see the result and neither can a screenshot, because low-contrast text is perfectly legible to the person who already knows what it says. It took the measurement to find that **undercover-pets.com, the children's domain, had the worst contrast on the site** (accent at 2.32:1 against a 4.5 floor) and that the fellowship palette's hover made a link *harder* to read than it was at rest. Deliberately outside `npm test`: it reads the generated `theme-*.css` files, so it is only correct after `npm run generate-themes`, and a check that fails because you have not run another script is a check people learn to ignore — which is why CI (not `npm test`) runs it, in a step that runs `generate-themes` first and also fails if regeneration changes any `theme-*.css` (the hand-edit drift check). One exemption, stated in the script: `solarized`.
- `check-related-terms.js` — a `related:` term is resolved by `glossaryUrl` (`.eleventy.js`) against page **titles**, and on a miss it falls back to `/glossary/` rather than erroring. So a stale term still renders a valid link to the wrong place: schema validation passes (related terms are free text), the build passes, and the link checker passes (the emitted URL is real). Retitling one lore or glossary page silently degrades every `related:` list naming it. Matching is exact — case, punctuation and leading articles included — so the script prints near-miss suggestions. It also warns (without failing) on duplicated page titles, where only the first is reachable.

`npm test` opens with a **unit-test suite** (`node --test test/*.test.js`, built-in `node:test`, no new dependencies — added 2026-08-24; extended 2026-08-27 with `test/markdown-containers.test.js` pinning the scene/POV fence-length rule a markdown-it-container bump could silently break, `test/storyline-threads.test.js` pinning `threadForSeason` and the registry invariants the privacy machinery assumes, and `test/image-size.test.js` pinning the header parser's null-rather-than-guess contract): `test/content-filter.test.js` pins `lib/content-filter.js`'s narrowing/private-thread truth tables (the one module where a regression ships content to the wrong readership — church-space, gated to the contemplative tier, appearing on a general-tier domain), and `test/classify-content.test.js` pins `lib/classify-content.js` — `classifyContentPath`, `isRelatedTopicPageIncluded` and `isContentIncluded`, extracted verbatim from `.eleventy.js` on the same date so they could be tested without booting Eleventy — including regression tests for the two documented real bugs (the layout-vs-inputPath hazard and the journal fallthrough). After that come the structural gates (there is no other linter beyond them): `scripts/check-changelog.js`, then **`scripts/check-changelog-coverage.js`** (added 2026-09-01 — the only step in `npm test` that **warns without failing**: it lists content pages whose path, slug or title appears nowhere in `CHANGELOG.md`, after an audit of all 674 first-parent commits found 24 pages that had shipped without ever being written down. It is deliberately not a gate, because whether a change deserves an entry is a judgement rather than a structural fact, and the obvious gate — a PR touching `src/` must touch `CHANGELOG.md` — is satisfiable by a junk line and would manufacture the appearance of coverage. It is useful only while the count normally reads zero, which is why the backlog was filed before it was wired in; if it is ever allowed to sit at a permanent nonzero number, retire it rather than learning to skip past it), then `scripts/validate-content.js` (front-matter schema validation across all Markdown content, **plus the image bookkeeping** — a missing `image:` target, an unreferenced file under `src/images/`, a stale `story-bible/images.md` slug, since 2026-08-15 **byte-identical duplicate images**, which fail rather than warn because sharing one picture between two pages takes one file and two references, never two files, and since 2026-08-21 **the URL the layout actually emits**, which is a different question from whether the file exists somewhere: each layout hardcodes its own `/images/<category>/` and appends the front-matter value, so a file one directory out passes the existence check by basename and still 404s on the page — as `drithane.jpg` did for four days; **plus each edition's hero cast**, which is the one check that crosses from content into `lib/editions.js`: a `heroCharacterIds` entry that names no page, names a page with no `image:`, or names a character that edition's own filter excludes silently shrinks or empties the slideshow, and four editions were listing casts they could render none of), then (since 2026-08-24) `scripts/check-internal-links.js` and `scripts/check-related-terms.js` (see their own bullets above), `scripts/sync-version.js --check` (fails if README's "Current version" line disagrees with `package.json`), and an Eleventy dry-run (catches template/build errors without writing `_site/`). CI (`.github/workflows/ci.yml`) runs `npm test` plus, on every PR: the theme-sync-and-contrast step (see check-contrast above), `shellcheck --severity=warning` over all five deploy scripts — `cpanel-deploy.sh`, `deploy-lib.sh`, `mail-lib.sh`, `ensure-node.sh` and `cpanel-autopull.sh` (this line named only two of them until 2026-08-13; the list had grown three times without it) — and a **shared-scripts job** that diffs the four shared deploy scripts against `dermot-cochran-photography`'s `main`: pre-existing drift fails, while a PR that is itself changing a shared script only warns, since the identical edit lands in the sibling as its own PR and one of the two has to merge first. The whole stack — layers, what each gate exists to catch, where each runs (npm test vs CI) and why, and the rules for extending it — is written up in **`TestingStrategy.md`** (added 2026-08-24): mechanics live there; the authority rules the gates serve stay in this file.

**Full-text search only works after `npm run build`** — Pagefind indexes the built `_site/` output, so the search box is a no-op under `npm run start`'s dev server.

The unit suites run individually (`node --test test/content-filter.test.js`), but the structural gates don't subdivide — `validate-content.js` always scans every content file, and `eleventy --dryrun` always builds every page. To iterate on one content file, use `npm run start` and visit that page directly.

## Architecture

**The site stays static, with no accounts and no logins — settled 2026-08-04.** Any reader-side state (a read-progress marker, a "continue reading" link) may only ever be client-local, e.g. localStorage per domain, and degrades to nothing without complaint; the **reading-mode switcher** (`src/js/presentation.js`, added 2026-08-21) is the worked example of the whole rule — a per-reader override of the domain's presentation mode, kept in one localStorage key, invisible without JS, and falling back to the edition's own mode whenever storage throws; anything requiring accounts, sessions, or server-side per-reader state is out of scope by design, not by omission. Comments are the one stateful feature and they deliberately live in GitHub's account system via giscus, not the site's. Don't propose accounts as the fix for a tracking or personalisation problem.

### Content pipeline

Every content type (character, lore entry, codex entry, glossary entry, chapter, journal entry) has **one schema, one source of truth**: `lib/content-schema.js`'s `CONTENT_TYPES` registry. Both `scripts/validate-content.js` (fails the build on a malformed file) and `scripts/new-content.js` (`npm run new`, scaffolds a new file) read from it, so they can't drift apart. Timeline entries are the one exception — they use `layout: base.njk` with hand-written HTML in the body rather than a dedicated layout/schema entry (`TIMELINE_TYPE` in the same file covers validation only; there's no scaffold for them).

Content lives under `src/` by type: `src/characters/`, `src/seasons/s<NN>/e<NN>/s<NN>e<NN>c<NN>.md` (chapters), `src/lore/` (with subdirs `planets/`, `universes/`, `worldwrights/`, plus a standalone `glossary/canonical-glossary-and-migration-guide.md` reference doc that is *not* part of the `glossary` collection), `src/glossary/` (the actual glossary-entry collection), `src/codex/`, `src/timeline/`, `src/journal/`, `src/threads/`. (A root-level `lore/` staging directory existed until commit `668d7bc` — "remove superseded root-level lore drafts". Don't recreate it; drafts belong in `story-bible/`.)

Key chapter front-matter fields (see `lib/content-schema.js` for the full/authoritative list):
- `id` (`s<NN>e<NN>c<NN>`) is *derived* from `season`/`episode`/`chapter` — `validate-content.js` fails the build if they disagree, or if the filename doesn't match.
- `comment_id` now has **two** consumers, both relying on the same property — that it is permanent and moves with the content. It is the giscus discussion's identity *and* the chapter's permanent citation URL, `/c/<comment_id>/` (`src/chapter-aliases.njk`), which exists because a chapter's `sNNeNNcNN` URL gets reassigned to different content by renumbering. Changing or regenerating one now breaks an external citation as well as a comment thread.
- `comment_id` is a **separate, permanent** identity for the giscus discussion thread, deliberately decoupled from `id`. Chapters get renumbered in place to keep story chronology consistent (see CHANGELOG's "renumbered" entries), which reassigns a URL like `/seasons/s00/e02/...` to different content — `comment_id` moves with the *content*, not the slot, so existing comment threads don't get silently reattached to something else. Set once by `npm run new -- chapter`; never regenerate it. `validate-content.js` fails the build on any `comment_id` collision across chapters.
- `date` (real-world `YYYY-MM-DD`, publication date) is distinct from `timestamp` (an in-universe free-text string) — `date` drives the Atom feed and is set automatically by `npm run new`.
- `povs: [{id, label}, ...]` lists which characters' viewpoints a chapter contains. An entry may carry `tier: contemplative` (any `TIER_ORDER` value; `validate-content.js` refuses others) to mirror a tier-gated block in the body — the chapter layout's "View from" buttons are filtered by it (`povsForTier`).

Chapter bodies use two custom markdown-it containers (`lib/markdown-containers.js`, shared by `.eleventy.js` and `src/_data/scenePovPages.js`):
- `::::: scene N` ... `:::::` — an optional scene wrapper (5 colons is convention; must be more colons than any nested `:::pov` block so markdown-it-container's fence-length rule can't close the scene early on a nested `:::` line). A chapter with no scene wrapper is treated as one implicit scene.
- `::: pov <character-id>` ... `:::` — one character's viewpoint within a scene. **`::: pov <character-id> tier=contemplative`** marks a block that renders only on a build whose edition sits at that tier or above (Dermot's direction, 2026-09-03: *the contemplative edition may have additional POV scenes for any chapter*). On every lower tier the renderer drops it from the token stream before rendering — absent, not a placeholder — so the chapter page, the scene-POV pages and the buttons all agree. The overlay rule that comes with it: every tier's reading of a chapter must be complete without the blocks the tier above adds, so a gated block may deepen or witness a chapter but nothing below may depend on it, and like Season 8 it carries no canon. The build's tier is its edition's `tier` (`lib/editions.js`); the canonical site is at the general tier.

`src/_data/scenePovPages.js` parses this token stream (not the rendered HTML) to flatten every `(chapter, scene, character)` combination into its own paginated page via `src/scene-pov.njk`, so readers can follow one character's POV in isolation or compare how different POVs render the same scene.

### Multi-domain deployment & content filtering

This repo deploys to **several independently-branded production domains** (cPanel Git Version Control clones) plus GitHub Pages, all from the same branch/build. Four mechanisms drive this (the count said two while three were listed, and is corrected here along with the fourth):

1. **`deploy.conf`** (untracked, copied from `sample-deploy.conf`, or from the two-key `sample-deploy-minimal.conf`) — per-clone config read by `scripts/cpanel-deploy.sh`. A single clone can also fan out to multiple `ALT_DOMAINS` (addon domains sharing the same cPanel account). See `TECHNICAL-README.md`'s "cPanel deployment config" section — it's the authoritative reference for every key; don't duplicate it here.
   - **A minimum viable `deploy.conf` is two lines** (`CPANEL_USER`, `DOMAIN`) since 2026-07-30. A domain's *identity* — `THEME`, `EDITION`, `CHARACTERS`/`TOPICS`/`THREADS`, `SITE_NAME`/`SITE_TITLE`, `COMMENTS_ENABLED`, `GISCUS_PROFILE` — is resolved from **`lib/editions.js` by domain** (`scripts/resolve-edition.js`) for any key the file leaves unset. `deploy.conf` still wins wherever it sets a value, and the deploy log prints each key's provenance.
   - **What stays server-side is what only the machine knows or should hold:** account name, which domains it serves, `ADMIN_EMAIL`, the raw `GISCUS_*_ID` values, and `CUSTOM_CSS_FILE`. What moved is every *decision* about a domain, so it's reviewable in a PR and can't be misconfigured silently on a server. `GISCUS_PROFILE` (repo-side) and the raw ids (server-side) fall on opposite sides deliberately — that's the seam for independent hosting.
2. **`lib/editions.js`** — the tracked registry of per-domain identity: deploy config plus copy and flourishes (homepage tagline, hero cast, footer audio, and — since 2026-09-01 — an optional `readingPlan`, a plain-register replacement for Sen's note on `/start/`, an optional `sectionHeroes` override for a section page's hero image, and an optional `excludedNotice`, plain-register placeholder copy that also drops the placeholder's cross-domain link — the pets edition is the one that carries all three, and `validateEditions` checks their shape). Keyed by `domains`. **`theme` is only a palette now**; `EDITION` is identity, and the two are independent axes because several domains share one palette. An untracked **`editions.local.json`** (template `sample-editions.local.json`) lets someone host this site on their own domain without maintaining a fork — same pattern as `giscus.local.json`.
   - **Governing rule: canon is centralised, variants are non-canonical.** Nothing an edition carries may assert a fact about the world; `src/seasons/`, `src/lore/` and `src/glossary/` are identical on every domain. The test for a proposed field is not "is this nice for that domain?" but "could two domains now disagree about something true?" This is what makes multi-domain coherent rather than merely convenient — filtering only ever *subtracts*, so a clone shows a subset of one record, never a contradiction of it. It's also why `CUSTOM_LORE_FILE` is deprecated: injecting a page into `src/lore/` per clone was the one route to per-domain canon, and there is deliberately no replacement.
3. **`THEME`** — `src/css/main.css` is the source of truth; `scripts/generate-themes.js` (`npm run generate-themes`) mechanically derives every `src/css/theme-<name>.css` from it by swapping only the palette variables. **Always run this after editing `main.css`'s structural CSS** (not just palette) so every theme stays byte-for-byte in sync outside its palette — editing a `theme-*.css` file directly will be overwritten.
4. **`PRESENTATION`** — a third axis, independent of both: identity (`EDITION`) is who a domain is, `THEME` is what colour it is, and the presentation mode is **how it wants to be read** — measure, leading, type size, density. Registered in `PRESENTATION_MODES` (`lib/editions.js`) and implemented as `:root` custom-property overrides in `main.css`, keyed off a `data-presentation` attribute `base.njk` writes onto `<html>`. Four modes: `story` (the default posture), `primer` (undercover-pets.com — big type, short measure, real tap targets), `archive` (fellowshipoflight.site — reference density) and `contemplative` (fellowshipoflight.org, church-space.site — the slowest setting on the site). **A mode is a posture, not a tier**, so it deliberately doesn't map one-to-one onto the audience tiers: starquest.site is the young-adult tier and reads a story straight through exactly as the general tier does. It moves only custom properties, which is what makes it compose with the palettes instead of multiplying against them — so put a mode's rules in `main.css` and let `generate-themes` propagate them, never in a `theme-*.css`. There is **no `deploy.conf` key** for it and it needs no deploy plumbing: it rides into the build with `EDITION`. **Readers can override it** from a "Reading" control in the header (`src/js/presentation.js` plus an inline restore script in `base.njk`'s `<head>`, which is what stops the page painting in one mode and jumping to another) — client-local, per-origin, gone without JS. Per-edition reader profiles and the full style guide: `story-bible/edition-reader-profiles.md`.

`lib/content-filter.js` implements `CHARACTERS`/`TOPICS`/`THREADS` narrowing (env vars, set by `cpanel-deploy.sh` from `deploy.conf`) plus the **tier gate** on storyline threads. Key behaviors:
- A **narrowed** build (`deploy.conf` sets `CHARACTERS`/`TOPICS`/`THREADS`) still builds every page at its normal URL — excluded pages render an "excluded.njk" placeholder rather than disappearing, so no link ever 404s.
- **A tier-gated thread is absent below its tier, and ordinary content at or above it** (Dermot's ruling, 2026-09-04, replacing `private: true` — `story-bible/intake-2026-09-04.md`). The one-line definition: ordinary content is **included unless a filter narrows it out**; a thread that names a `tier` in `lib/storyline-threads.js` is **excluded on every build whose edition sits below that tier, whatever the filter says**, and on a build at or above it is ordinary content like everything else. The gate is the same predicate the tier-marked `::: pov` blocks use (`tierVisible` in `lib/editions.js`), applied to a whole thread, and the build's tier is its edition's — so the canonical site, GitHub Pages, local dev and every third-party fork, which all resolve the default edition at the general tier, never show a contemplative thread, and no `deploy.conf` value can open it. Note where the gate lives versus where the effect lands: it is declared only on a **thread**, but individual **pages** acquire it by membership — a chapter through its season, a character/lore/codex/glossary/timeline page through its tags or category, a thread landing page or Season 8 index through an explicit `threadId` (`gatedThreadForPage`). Excluded here means the same as everywhere else in this system: the page still builds at its normal URL as an `excluded.njk` placeholder pointing at the thread's `homeDomain`, so no link 404s. What retired with the flag: the "excluded unless named in" case, and the validator's public-to-private link boundary — a general-tier page may link into the thread and gets the ordinary placeholder.
- `church-space` is the only gated thread (`tier: "contemplative"`) and is meant to stay that way — it exists because that overlay belongs to the contemplative readership, not because gating is a general per-deploy feature. Every other per-domain difference is `deploy.conf` filtering or the tier ladder in `lib/editions.js`; reach for those first, and treat gating a second thread as a design decision rather than configuration.
- `.eleventy.js`'s `eleventyComputed` override drives inclusion — it classifies a page by `inputPath` (`classifyContentPath`), **not** by `data.layout`, because `layout` is itself one of the fields being overridden and its resolution order isn't guaranteed relative to other computed fields (see the long comment at the top of `.eleventy.js` — this bit was a real, subtle bug).
- `lib/storyline-threads.js` (`STORYLINE_THREADS`) is the single registry of storyline threads and which season numbers belong to each; `threadForSeason()` is the canonical season→thread lookup, exposed as an Eleventy filter and consumed by both the `/threads/` site section and the deploy-time filter.

- A **scene-POV page follows its character, not its chapter** (`isCharacterPovIncluded`, since 2026-09-02): it is real content when the witness is named in `CHARACTERS` or their own character page is included by the build's tags — never merely because the chapter is. Until then only `CHARACTERS` could grant one, and undercover-pets.com (which narrows by topic and thread and names no characters) shipped every one of its 57 "View from" pages as a placeholder.

If you add a new content-bearing field or page type, check whether it needs to participate in `isCharacterIncluded`/`isChapterIncluded`/`isTopicPageIncluded`/`isThreadIncluded` (`lib/content-filter.js`) and `classifyContentPath` (`.eleventy.js`) — otherwise it'll silently always/never be included under a narrowed deploy.

## Content authoring conventions

- Prefer `npm run new` over hand-writing front matter — it scaffolds the correct shape per `lib/content-schema.js` and, for chapters, sets `date` and generates `comment_id` automatically.
- Never regenerate an existing chapter's `comment_id`, even when renumbering — see "Content pipeline" above.
- Timeline entries (`src/timeline/*.md`) have no scaffold; copy an existing one's front matter (`title`, `sort_order`, both required) and hand-write the HTML body.
- **Existing canon changes only by extension, clarification, or genuine dilemma** (Dermot's direction, 2026-08-25). Published canon — lore and narrative alike — is not intentionally changed otherwise. An edit to a published canon page must be one of three things: an **extension** (adds without altering what stood), a **clarification** (says better what was already true), or the resolution of a **genuine dilemma** (canon commitments that cannot all stand). Anything else is new material, or it is nothing. This names a practice the corpus already ran on rather than a new regime — genuine errors in arithmetic, chronology or terminology were already fixes (a clarification in this sense), chartered works were already superseded-not-retconned, and every published chapter already binds. Worked example from the day of the ruling: an in-session direction that would have reopened `umbral-moon.md`'s "do not have a from" position was put back to Dermot and dropped in favour of the entry as published, because nothing forced the change. The operational habit that follows: before editing a published canon page, say which of the three the edit is; if it is none of them, it waits. **Addendum, same day: a genuine divergence may be realized differently in different formclusters.** Resolving a dilemma need not mean one horn wins everywhere — the cosmology supplies the escape valve, because two formclusters share no arena (`src/glossary/formcluster.md`): realizations seated in different clusters cannot meet to contradict each other, and the record's own reach ends at its cluster's edge, so the home record states its realization plainly while the other stands as structure rather than observation. Two bounds keep this honest. It is a device for **genuine dilemmas only**, never a general licence to fork canon per cluster — and it is in-world structure, a different axis entirely from the editions rule that canon is centralised and variants non-canonical: every domain still shows one record, and that record may itself say "here it is thus; a differently-seated cluster could realize it otherwise."
- **Four canon statuses** (see `story-bible-summary.md`'s canon-status table). **Canon** — the published seasons, plus lore and the glossary: binding. **Valid-for-its-author** — the Codex: a named source's account, filed inside the record, not binding. **Overlay** — currently only `church-space`: a devotional commentary layer laid *across* the whole record rather than a document inside it, reading the same events through a declared lens, opted into per domain and never load-bearing for the main story. An overlay is neither canon nor codex; don't file overlay material as either, and don't let the main story come to depend on it. **Chartered** (settled 2026-07-26) — approved derivative work by another hand, above a fan work and below canon, governed by one rule: **canon binds it; it does not bind canon.** Consistent with canon as it stood at approval; superseded rather than retconned when later canon contradicts it; never load-bearing; carries no `canon_facts`. What separates the four is *who wrote it and where they stand* — Codex is in-universe authorship, Overlay is a lens across the same events, Chartered is new events by another hand, out-of-universe and endorsed. **None exist yet**, and the repo will **register** chartered works rather than host them (a third party's work has a different rights holder — filing it under `src/` would put it inside a CC BY-NC-ND scope Dermot can't license). Related but independent: fan images and music may be linked from the site as **referenced, not endorsed** — a link is a pointer, not approval, and referencing something never makes it chartered.
- **Codex viewpoints add flavour and in-character debate — never doubt about canon** (Dermot's ruling, 2026-08-21). This bounds the rule below rather than contradicting it. An entry may be partial, self-serving, devotional or mistaken *in its author's voice*, because that is what gives the Codex its texture; what it may never do is leave the reader unsure what is actually true in the world. The test is the reader, not the author: after reading, is canon **less settled** than before? If yes, the entry has overstepped, however well-attributed it is. Two habits keep the line: state the record's own position plainly where one exists rather than staging an unresolved contest between equals, and let a tradition keep its language without conceding that the thing the language names is an open question. `src/codex/the-borrowed-silhouette.md` is the worked example — it says outright that the category it examines cannot be occupied, and still lets the devotional annotation have the last word, because the annotation disputes the filing rather than the finding.
- **The Codex is not canon; each entry is canon-*for-its-author*.** This is the rule that makes the lore/codex boundary below work, and it cuts both ways. A codex entry is never the story asserting a fact — it is a named in-universe source's account, and it may be wrong, partial, self-serving, devotional, or flatly contradicted by `src/lore/`, by a chapter, or by another codex entry. What it may *not* be is arbitrary: it has to be a document that source would actually have produced, valid by their own lights — their era, their access, their institution's house style, their blind spots, the things they have reason to omit. Test an entry by asking "could this person have known this, and would they have written it this way?", not "is this true?". Two consequences: `author` is a **required** field on every codex entry (`lib/content-schema.js` enforces it — an entry with nobody behind it has no point of view to be valid from and silently becomes Archive-voice fact); and codex entries carry **no `canon_facts`**, unlike chapters, because they establish nothing. Ratification of the seasons as canon (2026-07-25) does not extend here.
- **Lore/codex boundary — always move inconsistencies or contradictions into the Codex, away from Lore.** Lore (`src/lore/`) and the glossary (`src/glossary/`) state settled, internally-consistent, hard-SF-leaning fact — the ground a reader can trust as flatly true. Any contested, paradoxical, devotional, or otherwise self-contradicting reading belongs in the Codex (`src/codex/`), filed as some named in-universe source's *account* or working paper rather than the Archive's single settled voice. When you notice two lore/glossary pages disagreeing (or one page arguing with itself), the fix is to relocate the contested material to the Codex and leave lore consistent — not to pick a winner inside lore. See the *"Sorting Doctrine Out of Lore"* journal entry and `story-bible/`'s editorial note for the worked precedent.
- **Explain gaps, inconsistencies and complexity in-story wherever possible** (Dermot's direction, 2026-08-15). A narrative gap, an apparent contradiction between two entries, or a tangle of overlapping names and tiers is **part of the story and should be answered from inside it**, not quietly tidied away and not left as an authorial shrug. The setting already supplies the machinery, and the rule is mostly an instruction to reach for it rather than invent a new one: the **Archive is an in-universe narrator with limits**, so *"the Archive has not established this and has not been asked to"* is a real answer, and a truthful one, in a way *"this is underspecified"* never is. The existing devices, in rough order of reach — the record declining to fix a date or a cause; [What the Record Refuses](src/lore/what-the-record-refuses.md) for whole classes of thing the setting will not carry; the **lore/codex boundary** above, which relocates a contested reading to a named source rather than picking a winner; the **three-way reading** for contested events (divine influence / purely physical account / dispute the transmission itself, the third being the one normally dropped); *valid-for-its-author* codex framing; and deliberate mysteries that stay shut until their own season. **Complexity gets the same treatment as contradiction.** Where a structure is genuinely tangled — many names for one tier, two bodies with overlapping mandates, an office answering on two axes — the tangle is usually evidence about the thing, and saying *why* it is tangled is better writing than smoothing it flat. Worked example: the Safety Corps' investigation authority looked like a flat contradiction of two charter lines and resolved on the word *cross-disciplinary*, which was more interesting than either line alone.

  **This does not override *"mark the absence; do not explain it"***, and the two are easy to mistake for opposites. Sen's [Marked Absences](src/codex/marked-absences.md) doctrine governs gaps **in the in-universe record**: where the Archive's knowledge stops, you mark it and invent no cause, because *"an explained gap invites the record to defend a guess forever."* This convention governs gaps **in the shape of the work** — two entries that appear to disagree, a name that has drifted, a structure a reader will find bewildering. The line between them is exact and worth holding: **explain the epistemology, never invent the fact.** Saying *why* the record is thin here — limited instruments, contested transmission, three traditions naming one thing differently, a question of the wrong shape — is explaining shape, and is welcome. Saying *what* the missing fact was is inventing, and Sen is right that it costs more than it pays. When in doubt, the absence stays marked.

  Two further limits. This licenses explaining a gap, never manufacturing one for effect. And it is **not** a licence to leave real errors standing: a genuine mistake in arithmetic, chronology or terminology gets fixed, not diegetically excused.

- `CHANGELOG.md` follows Keep a Changelog + SemVer; update it under `[Unreleased]` for any lore/canon change, deploy feature, or fix worth noting to a reader of the changelog (this project has never needed a MAJOR bump — everything so far has been additive/backward-compatible).

- **Thread vs. strand vs. arc** (settled 2026-07-25 — full table and migration map in `story-bible/story-bible-summary.md`'s Narrative Structure section). A **storyline thread** is the macro concept and the only one with engine consequences: it groups whole *seasons*, is registered in `lib/storyline-threads.js`, and drives `/threads/`, `threadForSeason`, `deploy.conf`'s `THREADS` narrowing, and private-thread hiding. A **strand** is the micro concept — two parallel storylines *inside one season*, separate POV casts, meeting at a fixed convergence point (Strand A / Strand B); story bible only, no id, no page, no registry. An **arc** is a character's trajectory over time and is not a reading path at all. A season has exactly one thread and any number of strands. Don't write "Thread A" for a within-season storyline; that usage is migrated.

## Before committing

Run `npm test` (schema validation + Eleventy dry-run) — CI enforces this on every PR and it catches most content mistakes (bad front matter, id/filename mismatches, duplicate `comment_id`s) before they become a broken build or a lost comment thread. If you touched any script under `scripts/` that CI shellchecks — `cpanel-deploy.sh`, `deploy-lib.sh`, `mail-lib.sh`, `ensure-node.sh`, `cpanel-autopull.sh` — also expect `shellcheck --severity=warning` to run in CI. The last four are **shared, byte-identical files**: change one in this repo and the same edit must land in `dermot-cochran-photography`, `diff`-clean, in the same piece of work — and since 2026-08-24 CI's shared-scripts job checks exactly that against the sibling's `main` (in both repos, pointing at each other), so forgetting the second half surfaces as a warning on the first PR and a failure on every later one.
